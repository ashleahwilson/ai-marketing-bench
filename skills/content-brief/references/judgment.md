# Judgment calls

What the script can't decide. Work through these before writing the brief and again before replying.

## Is there enough to write it?

Three things must be known before a brief is worth writing: the **goal**, the **audience** and the **CTA action**.

| Missing | Do this |
|---|---|
| Goal or CTA action | Ask. The goal is the user's decision; brand memory can suggest options but can't choose |
| Audience, and brand memory has one clear segment the request fits | Use that segment and say so in one line |
| Audience, and brand memory has several segments or none | Ask |
| CTA URL only | Write the brief with `→ TBD: URL` and list it under Open before writing |
| Publish date, channel, length | Don't block. Use `TBD`, or the channel's rule for length |

**One round, at most four questions,** numbered, each answerable in a few words. Offer the likely answer from brand memory where there is one ("Is the CTA the free month-end review, or something else?"). Don't write a brief file while you wait.

**The user said "don't ask", "just draft it" or similar:** write it, mark the unknowns `TBD`, set `Status: draft (gaps marked TBD)` and list the gaps first in the reply. Never fill a gap with a plausible guess.

## Does the request fit the brand?

Read `brand/audiences.md` (Segments, Not for), `offer.md` (We don't do) and `BRAND.md` (Who it's not for).

If the requested audience is one the brand says it doesn't serve, or the requested offer isn't in brand memory (a demo, a trial, a plan that doesn't exist):
- Don't write the brief.
- Say what brand memory records, in one line, with the file.
- Offer the nearest brief that fits (the same topic for a served segment), and ask whether the offer has changed. If it has, recommend updating brand memory first (the brand-memory skill) so every other skill sees it.

A user-stated offer that brand memory simply doesn't mention (a free trial for a brand whose memory lists only plans) is the user's fact: use it, mark it "from the request", and suggest recording it.

## Can the topic stand on confirmed facts?

Check every claim the topic leans on against `claims.md`, `proof.md`, `rules.md` and `offer.md`.

- **Held by a rule or listed as "Needs substantiation":** it can't be a key message, must-include, headline or outline point. Say why in one line, name what would substantiate it (the substantiation note in `claims.md`), and offer either a reframed brief on confirmed facts or holding the piece. Don't write the held claim's figures anywhere except under Avoid.
- **Confirmed:** use it, with its source under Sources to use.
- **Not in brand memory at all:** treat it as unsupported. It goes under Open before writing with "needs a source", never into Must include.

If the topic has nothing confirmed to stand on, recommend not writing the piece yet, and say what proof would unlock it.

## Must-includes

Each item must be one of:
1. A line tagged `confirmed` in brand memory.
2. A fact the user stated in the request.

Then check each one:
- **Third-party statistics** the user supplies ("60% of restaurants close in year one") need a link to the original source before they can run. Move them to Open before writing: "needs a cited source; include only with the link". Don't confirm them from memory, even when they sound familiar.
- **Quotes** are copied word for word from `proof.md`. If `named:` is `no` or `unconfirmed`, the brief says so: use the quote unattributed, or name the customer only after their OK.
- **Prices** must be the right plan for this audience ($349 single location is not the $299 group rate).
- **Provisional or assumed** brand facts are not must-includes. List them under Open before writing for confirmation.
- Never add an incentive, deadline, guarantee or result the user didn't give.

## Keywords and search data

- **No data supplied:** pick the primary keyword from the topic, in the reader's words. Under Search, write `Keyword status: unvalidated` and name what would validate it (an export from their keyword tool, or Search Console queries). Give no volumes, difficulty scores, rankings, traffic estimates or "high-volume" labels. If the user asked for numbers, say in the reply that you don't have their data and won't estimate, then still deliver the brief.
- **Data supplied:** choose from it. Quote any figure exactly as written, with the file. Never add a figure for a keyword that isn't in the data.
- **A keyword that breaks a brand rule** (it contains a banned promise or a never-use word) is ruled out even if it has the most volume. Say why in one line.

## Length, channel and voice

- Use the channel rule in `brand/voice.md` for length and style (email under 120 words, LinkedIn under 150 words, no hashtags, no exclamation marks). Carry those rules into Avoid.
- Without a rule, use a typical range (and call it that to the user): blog 700–1,200 words, landing 300–600, email 80–150, LinkedIn 80–150, newsletter section 150–300.
- Write the brief itself in the brand's spelling convention.

## Self-check questions

Answer each one before replying. A "no" means fix the brief, not hedge in the reply.

1. Could every must-include be pointed to in `brand/` or the request?
2. Is every figure in the brief from brand memory, the user's data or the request?
3. Is anything held, provisional or banned in a field or the outline (outside Avoid)?
4. Is the keyword marked unvalidated unless the user supplied data?
5. Is every gap a visible `TBD` with an owner, not a guess?
6. Would a writer who has never met the brand produce something content-qa-gate passes?
